# k6 + Kubernetes HPA: Step-by-Step Test Guide

## 1. What you need

You need:

* A running Kubernetes cluster
* Your REST API deployed in Kubernetes
* An HPA configured for the API
* Access to the API endpoint
* `kubectl`
* `k6`

For the first test, it is easiest to run k6 **from your local machine** and send requests to an endpoint that is reachable from your machine.

---

## 2. Install k6

Follow the official installation instructions for your operating system:

https://grafana.com/docs/k6/latest/set-up/install-k6/

Verify the installation:

```bash
k6 version
```

You should see something similar to:

```text
k6 v1.x.x
```

---

## 3. Create a simple test

Create a file:

```text
api-test.js
```

Start with a simple endpoint such as `/health` or another lightweight API endpoint.

```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [
    { duration: '1m', target: 5 },
    { duration: '2m', target: 10 },
    { duration: '2m', target: 20 },
    { duration: '2m', target: 5 },
    { duration: '1m', target: 0 },
  ],

  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500'],
  },
};

export default function () {
  const response = http.get('http://YOUR-API-ENDPOINT/health');

  check(response, {
    'HTTP status is 200': (r) => r.status === 200,
  });
}
```

Replace:

```text
http://YOUR-API-ENDPOINT/health
```

with your actual API endpoint.

---

## 4. Run the test

Run:

```bash
k6 run api-test.js
```

k6 will display something similar to:

```text
http_reqs......................: 12000
http_req_duration..............: avg=120ms
                                 p(95)=250ms
                                 p(99)=400ms
http_req_failed................: 0.10%
checks.........................: 99.90%
```

The most important values initially are:

* `http_reqs` → number of requests
* `http_req_duration` → response time
* `p(95)` → 95% of requests were faster than this
* `http_req_failed` → failed request percentage

# 5. Check your HPA before testing

Before starting the load test, check the HPA:

```bash
kubectl get hpa
```

For example:

```text
NAME        REFERENCE          TARGETS    MINPODS   MAXPODS   REPLICAS
api-hpa     Deployment/api     20%/70%    2         10        2
```

You can also continuously monitor it:

```bash
kubectl get hpa -w
```

In another terminal, monitor the pods:

```bash
kubectl get pods -w
```

And optionally monitor CPU/memory:

```bash
kubectl top pods
```

You should have something like this running while k6 is running:

```text
Terminal 1:
k6 run api-test.js

Terminal 2:
kubectl get hpa -w

Terminal 3:
kubectl get pods -w

Terminal 4:
kubectl top pods
```

---

# 6. Run the load test

Start k6:

```bash
k6 run api-test.js
```

While it is running, watch the HPA.

You might see:

```text
2 replicas
   ↓
CPU increases
   ↓
HPA target exceeded
   ↓
3 replicas
   ↓
5 replicas
   ↓
7 replicas
```

This is the main thing you want to verify.

The API should continue responding successfully while the HPA adds pods.

---

# 7. Test scale-down

After the high-load stage finishes, k6 reduces the traffic.

For example:

```text
20 users
   ↓
50 users
   ↓
100 users
   ↓
20 users
   ↓
0 users
```

Watch:

```bash
kubectl get hpa -w
```

You should eventually see the replicas decrease.

For example:

```text
REPLICAS
2
4
6
8
6
4
2
```

The exact timing depends on your HPA configuration, especially its stabilization and scale-down settings.

---

# 8. Make the test stronger

Once the basic test works, increase the load gradually.

For example:

```javascript
stages: [
  { duration: '2m', target: 10 },
  { duration: '3m', target: 25 },
  { duration: '3m', target: 50 },
  { duration: '3m', target: 100 },
  { duration: '3m', target: 200 },
  { duration: '5m', target: 10 },
  { duration: '2m', target: 0 },
]
```

Don't immediately jump to an extremely high load.

Increase it gradually so you can identify when:

* HPA starts scaling
* latency starts increasing
* errors appear
* maximum replicas are reached

---

# 9. Add realistic API requests

Testing only `/health` is useful for your first test, but it may not represent the real workload.

For the actual performance test, use an API operation that represents normal control-plane usage.

For example:

```javascript
export default function () {
  const response = http.get(
    'http://YOUR-API-ENDPOINT/api/resources'
  );

  check(response, {
    'status is 200': (r) => r.status === 200,
  });
}
```

If your API requires authentication:

```javascript
const params = {
  headers: {
    Authorization: `Bearer ${__ENV.API_TOKEN}`,
  },
};

export default function () {
  const response = http.get(
    'http://YOUR-API-ENDPOINT/api/resources',
    params
  );

  check(response, {
    'status is 200': (r) => r.status === 200,
  });
}
```

Run it with:

```bash
k6 run -e API_TOKEN="your-token" api-test.js
```

Don't commit the token into the JavaScript file.

---

# 10. Define your pass/fail criteria

Before running the final test, define what "successful" means.

For example:

```text
Expected load:          100 concurrent users
p95 response time:      < 500 ms
HTTP error rate:        < 1%
Minimum replicas:       2
Maximum replicas:       10

HPA:
- Must scale out when CPU exceeds target.
- Must scale back down when traffic decreases.
- API must remain available during scaling.
```

Then your test has an objective result.

---

# 11. What to record

For each test, record something like:

| Metric           | Result  |
| ---------------- | ------- |
| Test duration    | 15 min  |
| Maximum load     | 100 VUs |
| Requests         | 50,000  |
| p95 latency      | 320 ms  |
| p99 latency      | 480 ms  |
| Error rate       | 0.2%    |
| Minimum replicas | 2       |
| Maximum replicas | 8       |
| HPA scale-out    | Yes     |
| HPA scale-down   | Yes     |

Also record any important observations, such as:

> At approximately 70 VUs, CPU exceeded the HPA target and the deployment scaled from 2 to 4 replicas. Response time remained below the defined 500 ms p95 threshold.

That is much stronger evidence than simply saying "the HPA worked."

---

# 12. One important detail: VUs vs. requests/second

When you are new to k6, this is easy to misunderstand.

If you configure:

```javascript
target: 100
```

that means **100 virtual users**, not 100 requests/second.

Each virtual user executes your `default` function repeatedly.

For example:

```text
100 VUs
  ↓
each VU executes HTTP request
  ↓
actual request rate depends on response time
```

If your requirement is specifically something like:

> "The API must handle 500 requests/second"

then you should use a k6 scenario designed around a controlled request rate rather than simply setting `target: 500`.

For example, k6's `constant-arrival-rate` or `ramping-arrival-rate` executors are useful for this.

---

# 13. Recommended final test

For your HPA requirement, I would eventually create a test with this structure:

```text
        Load
         │
         │       ┌───────────────┐
         │      /                 \
         │     /                   \
         │    /                     \
         │___/                       \____
         └──────────────────────────────────> Time

       Baseline    Load       Stress    Recovery
```

Specifically:

```text
1. 2 min   → low load
2. 5 min   → normal load
3. 5 min   → high load
4. 5 min   → stress load
5. 5-10 min → low load
```

During the entire test:

```text
k6
 ↓
API performance

kubectl get hpa
 ↓
HPA scaling

kubectl get pods
 ↓
pod count/readiness

kubectl top pods
 ↓
CPU/memory
```

Then compare the results against your predefined thresholds.

## Final goal

You want to be able to demonstrate:

```text
Load increases
      ↓
API CPU increases
      ↓
HPA detects threshold
      ↓
Pods increase
      ↓
API continues handling traffic
      ↓
Load decreases
      ↓
Pods decrease
      ↓
API remains healthy
```

That is the core evidence that your **REST API + Kubernetes HPA + performance test** is working correctly.
